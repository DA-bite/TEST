How the pipeline works

One workflow file does everything. This page walks through .github/workflows/deploy.yml in the order it runs.

The shape of it

The workflow has two jobs. Build and test checks out the code, builds the site, tests it and uploads the result. Deploy takes that upload and publishes it. Deploy waits for the first job, so a failing test means nothing is published.

Triggers

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

A push to main runs the full pipeline. A pull request aimed at main runs the build and tests so you see problems before merging. workflow_dispatch adds a Run workflow button on the Actions tab, which is useful for redeploying without a new commit.

Permissions

permissions:
  contents: read
  pages: write
  id-token: write

contents: read lets the job read the repository. pages: write and id-token: write let the deploy job publish to Pages and prove who it is. Nothing here can change your code.

Concurrency

concurrency:
  group: pages-${{ github.ref }}
  cancel-in-progress: false

Runs on the same branch queue up instead of running at once, and a deployment that has started is never cancelled halfway. Pull requests have their own group, so a review build never waits behind a deploy.

The build and test job

These steps run in order. If one fails, the rest are skipped.

StepWhat it does
actions/checkout@v4Downloads the repository
actions/setup-node@v4Installs Node 20
actions/configure-pages@v5Reads the Pages settings and exposes the path the site is served from. Skipped on pull requests
npm run buildTurns site/ into dist/
npm testChecks every page in dist/
actions/upload-pages-artifact@v3Packages dist/ for deployment. Skipped on pull requests

Why the build needs the Pages path

- name: Build site
  run: npm run build
  env:
    SITE_BASE: ${{ steps.pages.outputs.base_path }}

Every page uses relative links, which work from any folder. The one exception is 404.html. GitHub serves it for any missing address, however deep, so relative links would point at the wrong place. The build writes the real path, such as /my-repo, into that one file. On a custom domain the path is empty and the links start at /.

The deploy job

deploy:
  if: github.event_name != 'pull_request'
  needs: build
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}
  steps:
    - id: deployment
      uses: actions/deploy-pages@v4

needs: build holds the job until the first one passes. The if line keeps pull requests from publishing. The github-pages environment is how GitHub records deployments, and the url line puts the live address on the run summary.

What the tests check

scripts/test.mjs reads every HTML file in dist/ and reports all the problems it finds in one go, so you can fix them together.

  • The required files exist: index.html, 404.html and .nojekyll.
  • Each page starts with a doctype and has a lang attribute, a charset, a viewport tag, a non-empty title and exactly one h1.
  • Ids are unique within a page.
  • Images have an alt attribute.
  • Every relative link, image, stylesheet and script points to a file that exists.
  • Every #anchor points to an id on the page it names, including links to other pages.
  • No {{root}}, {{base}} or include markers are left in the output.

External links such as https://github.com are not fetched. A flaky network shouldn't block a deploy.
